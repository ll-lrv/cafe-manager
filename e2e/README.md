# 브라우저 E2E 시나리오

실제 브라우저(설치된 Chrome)로 가입부터 발주까지 화면을 직접 눌러 보며 확인하는 스크립트다.
필요한 곳은 DB 값도 직접 조회해서 맞는지 본다. 전체 7개 시나리오, 216개 항목.

## 실행

먼저 로컬 Supabase와 개발 서버를 띄운다 (`docs/HANDOVER.md` §3).

```
npx supabase start -x imgproxy,edge-runtime,logflare,vector,supavisor
pnpm dev
```

다른 터미널에서:

```
pnpm e2e                                   # 전체 (저장소 루트에서)
pnpm --filter @cafe/e2e e2e:sales          # 시나리오 하나
cd e2e && node run-all.mjs sales orders    # 여러 개 골라서
```

- 결과: 시나리오마다 `✔/✖ 이름 통과 n 문제 n`. 하나라도 실패하면 종료 코드 1
- 스크린샷: `e2e/shots/<시나리오>/` (git 제외)
- 시나리오 하나를 직접 돌리면(`node sales.mjs`) 항목별 `PASS`/`FAIL` 이 모두 나온다

### 설정 (환경 변수, `config.mjs`)

| 변수 | 기본값 |
|---|---|
| `E2E_BASE_URL` | `http://localhost:3000` |
| `CHROME_PATH` | `C:/Program Files/Google/Chrome/Application/chrome.exe` |
| `E2E_DB_CONTAINER` | `supabase_db_cafe-manager` (DB 확인용 `docker exec ... psql`) |

`playwright-core` 는 브라우저를 내려받지 않는다. 설치된 Chrome 을 쓴다.

## 알아둘 것

- **실행할 때마다 새 계정·매장을 만든다** (`owner<시각>@test.kr` 등). 로컬 DB에 테스트 데이터가 쌓이며, 비우려면 `pnpm db:reset` (모든 데이터 삭제)
- 서로 독립적이라 어떤 순서로 돌려도 된다. 다만 같은 DB를 쓰므로 동시에 여러 개를 돌리지는 않는다
- 콘솔의 `caret-color: transparent` hydration 경고는 Playwright 스크린샷이 넣는 스타일 때문이라 무시한다. 404 테스트가 내는 `status of 404` 도 의도된 것이다 (`run-all.mjs` 가 걸러낸다)
- 알림(토스트)은 화면 갱신보다 조금 먼저 뜰 수 있다. 알림을 본 직후 화면 내용을 확인할 때는 그 내용이 나타날 때까지 기다린다
- 세션 중 임시로 만든 스크립트를 옮긴 것이라 시나리오마다 도우미 함수(가입, 품목 만들기 등)가 중복돼 있다. `@playwright/test` 로 정식 전환할 때 공통 fixture 로 묶는다 (`docs/HANDOVER.md` §10)
