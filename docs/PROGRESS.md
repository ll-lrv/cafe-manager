### 3. 품목 관리
- 화면: `/items`(목록·검색·카테고리 필터·보관 품목 보기), `/items/new`, `/items/[id]`(입고 단위 + 품목 정보 + 보관), `/items/categories`(추가·이름 변경·순서·삭제)
- 데이터 접근 `apps/web/src/lib/api/catalog.ts`, 서버 액션 `app/(app)/items/actions.ts` (`catalog:manage` 확인)
- 직원은 목록·상세 보기만 가능 (입력칸 비활성, 관리 버튼 숨김, 관리 주소 직접 접근 차단)
- 입고 단위: "1봉 = 1,000g" 형태, 기본 입고 단위는 품목당 하나 (첫 단위는 자동 체크)
- 품목은 삭제하지 않고 보관(archived_at). 카테고리를 지우면 품목은 미분류가 된다
- 마이그레이션 `catalog_triggers`
  - `updated_at` 자동 갱신 트리거 (items, suppliers, menus, purchase_orders). Drizzle `$onUpdate` 는 ORM 으로 수정할 때만 동작해서 추가함
  - 입출고·레시피에 쓰인 품목은 기본 단위(g/ml/ea) 변경 차단 (화면에서도 잠금)
- 공용 `useFormAction` (`components/form-parts.tsx`): `<form action>` 은 제출 후 결과와 상관없이 입력칸을 비우므로, 오류가 나도 입력값이 남도록 직접 제출한다. 새 폼은 이것을 쓴다
- 루트 `db:*` 스크립트를 `npx supabase` 로 수정 (전역 supabase CLI 없이 동작)
- 브라우저 E2E로 확인: 카테고리 CRUD·순서·중복 안내 → 품목 추가(쉼표 숫자) → 단위 추가·기본 변경·삭제·중복/0 거부 → 수정·updated_at → 중복 이름 시 입력값 유지 → 검색·필터 → 기본 단위 잠금(화면+DB 트리거) → 보관/복원 → 직원 보기 전용 → 404 → 모바일 레이아웃

### 4. 입출고 기록 (DB 함수로 트랜잭션 처리)
- **결정 (2026-10-06)**: 여러 행을 함께 쓰는 작업은 DB 함수로 묶는다. 함수 목록과 NestJS 전환 방법은 **`docs/db-functions.md`**
- DB 함수 `record_stock_movement`: 단위 환산·단가 환산·로트 생성·유통기한 순(FIFO) 차감·원장 기록을 한 트랜잭션으로. 품목 행을 잠가 동시 기록에도 안전
- `stock_movements`, `stock_lots` 직접 INSERT 정책 제거 → 함수로만 기록
- 권한 `stock:adjust`(사장·매니저) 추가. 직원은 입고·사용·폐기만
- 화면 `/stock`: 입고·사용·폐기·조정, 품목 선택(카테고리별), 단위 선택(입고는 기본 입고 단위), 현재 재고 → 기록 후 재고 미리보기, 마이너스 경고, 입고 단가·유통기한, 최근 기록 50건(`?item=` 으로 품목별)
- 품목 상세: 현재 재고(부족 배지), 최근 기록 10건, "입출고 기록" 버튼
- 데이터 접근 `apps/web/src/lib/api/stock.ts`
- 확인: SQL로 함수 직접 검증(사장·직원·다른 매장 사용자, 로트 배분, 오류 문구, 직접 INSERT 차단) + 브라우저 E2E(입고→로트별 사용→마이너스 경고→조정→품목 상세→직원 기록→보관 품목 제외→모바일)

### 5. 재고 현황 + 실시간 반영
- core `stock-status.ts`: 재고 상태(없음·부족·충분), 유통기한 상태(지남·임박 3일·충분), 남은 날 표시, 시간대 기준 오늘 날짜 (테스트 16개)
- `lib/inventory.ts`: 품목별 재고·유통기한 상태 계산. 유통기한 "오늘"은 매장 시간대(Asia/Seoul) 기준
- 품목 목록(메뉴 이름 "품목·재고"): 현재 재고, 재고 없음/부족 배지, 가장 빠른 유통기한 배지, 상태 필터(`?status=low|expiry`)
- 품목 상세: 유통기한별 남은 양(로트), 부족 기준 표시
- 대시보드: 부족한 품목, 유통기한 확인(로트별), 최근 기록, 입출고 바로가기
- 실시간: `lib/api/realtime.ts` + `components/realtime-refresh.tsx` (앱 레이아웃). 다른 기기의 기록이 약 1초 안에 반영되고, 입력 중인 폼 값은 유지
  - 주의: 브라우저 클라이언트는 쿠키 세션 토큰을 Realtime 에 자동으로 넣지 않는다. 넣지 않으면 익명으로 구독되어 RLS 에 막혀 이벤트가 오지 않는다 → 구독 전에 `realtime.setAuth(access_token)`
- 확인: 브라우저 E2E (대시보드 집계, 목록 필터, 로트 표시, 직원 기기 기록 → 사장 화면 실시간 반영, 모바일) + 품목·입출고 E2E 회귀

- 대시보드: 오늘 매출, 판매 입력 바로가기. Realtime 에 sale_records 추가 (삭제는 필터 구독에 안 옴)

### 14. CSV 판매 가져오기 (2026-10-08)
- 유료화 순서 ③. 판매를 매일 손으로 넣지 않도록 POS 내보내기 파일을 올린다. 메뉴 "판매" → "CSV 가져오기" `/sales/import` (사장·매니저, 권한 `sale:import`)
- 흐름: 파일 선택(UTF-8·EUC-KR, 쉼표·탭) → 열 맞추기(열 이름으로 자동 추측, 제목 줄 건너뜀, 미리보기·읽지 않은 줄과 이유) → 메뉴 맞추기(같은 이름·저장해 둔 매칭은 자동, "가져오지 않음") → 가져오기(500건씩, 진행 표시) → 가져오기 기록·취소
- 날짜 형식: `2026-10-07`, `2026.10.07 13:05`, `2026/10/07 오후 1:05:09`, `20261007`, `2026년 10월 7일` + 따로 있는 시각 열. 금액 열이 없으면 메뉴 가격 × 수량
- 중복 방지: 행 키(날짜·시각·주문번호·이름·수량·금액 + 같은 내용 몇 번째) → `sale_records.external_id`. 같은 파일·겹치는 기간 파일을 다시 올려도 새 줄만. 모두 이미 있으면 빈 가져오기 기록은 지운다
- 스키마: `sale_imports`(가져오기 한 번), `menu_aliases`(파일의 메뉴 이름 → 메뉴, null = 가져오지 않음), `sale_records.import_id`(cascade), 뷰 `sale_import_summaries`
- DB 함수 `import_sales` (`docs/db-functions.md`). 가져오기 취소는 `sale_imports` 삭제 → 판매 → 원장 cascade. 판매 취소 방송 트리거는 가져온 판매를 건너뛰고 가져오기 취소 때 한 번만 방송
- core `sales-import.ts` (테스트 6개 추가, 37개). 판매 목록에 "CSV" 표시
- 토스 포스 형식은 공식 안내 글로만 확인(매출 엑셀의 "상품 주문" 시트: 상품명·옵션·수량·실판매금액). 실제 파일로는 확인 못 함
- E2E `orders` 의 가끔 재시도 원인 하나(입고 완료 알림 직후 화면 읽기)를 고침
- 확인: SQL 검증(중복 키 건너뜀, 오류 문구, 다른 매장 사장·익명 거부, 다른 매장 메뉴 매칭 거부, 취소 cascade) + 새 E2E 시나리오 `sales-import`(제목·취소·합계 줄, 열 자동 선택, 매칭·기억, 재고 차감, 같은 파일 다시, 겹치는 파일·미래 날짜, 가져오기 취소, 직원 차단, 모바일) + 전체 E2E 12개

### 15. CSV 가져오기: 취소·반품 반영 (2026-10-08)
- 취소·반품 줄(수량이나 금액이 음수)을 건너뛰지 않고 **음수 판매**로 기록: 매출에서 빼고 레시피 재료를 되돌린다(`sale` 원장 +, 로트 없이). 이론 vs 실제·매출 합계가 자동으로 상계된다
- 상태 열(결제상태·주문상태·취소여부 등, 자동 추측)이 "취소/환불/반품"인 주문 줄 → 판매 + 취소 두 줄. 예전에 "완료"로 가져온 같은 주문은 판매 줄이 중복으로 건너뛰어지고 취소 줄만 들어가 상계된다
- 스키마: `sale_records.quantity <> 0`, 원장 `sale` 부호 제약 완화(`..._sale_refunds.sql`). `import_sales` 재작성(`..._import_sales_refunds.sql`) — 같은 날 다른 세션이 만든 "하나씩 취소한 판매는 다시 안 가져오기"(`cancelled_sale_keys`)를 합쳐 둠
- 화면: 미리보기·메뉴 맞추기·요약에 취소 줄 수, 판매 목록 "취소" 표시, 취소 기록은 "지우기"(재료 다시 차감)
- 직접 입력(`record_sales`)은 그대로 양수만
- 리뷰에서 찾은 문제 2개 수정 (`..._cancelled_sale_keys.sql`, `..._sale_cancel_keys.sql`)
  - 가져온 판매를 하나만 취소하면 다른 기기에 실시간 반영되지 않던 것 (취소 방송 트리거가 가져온 판매를 모두 건너뛰었음) → 가져오기 기록이 남아 있으면(개별 취소) 방송, 가져오기 전체 취소의 cascade 만 건너뜀
  - 하나만 취소한 판매가 겹치는 파일을 다시 올리면 되살아나던 것 → 그 행 키를 `cancelled_sale_keys` 에 남기고 `import_sales` 가 건너뜀. 되돌리려면 직접 입력
  - E2E `sales-import` 에 단계 추가. 트리거를 예전 조건으로 바꾸면 실시간 확인이 실패하는 것 확인
- 확인: core 테스트 38개, E2E `sales-import`(취소 줄 상계, 상태 "취소" 주문 상계, 다른 세션의 개별 취소 단계 포함)·`sales`·`reports` 통과

  - 적용 순서 늘리기 → 바꾸기 → 추가. 메뉴에 없는 재료를 바꾸거나 늘리는 규칙은 그 메뉴에 아무것도 안 한다. 같은 옵션에 같은 재료를 두 번 바꾸기·늘리기·추가는 막는다
  - 옵션 상세에 "메뉴별 원가 변화" (이 옵션으로 재료가 바뀌는 메뉴, 원가 960원 → 1,320원)
- 판매 입력: 메뉴 줄의 옵션 버튼 → 옵션 체크 → "옵션 붙여 1개 더하기"로 메뉴 아래에 옵션 묶음 줄(± 수량, 지우기). 차감 미리보기·합계 금액에 옵션 반영. 판매 목록에 "카페라떼 + 샷 추가"
- 스키마: `menu_options`, `menu_option_rules`(enum `option_rule_kind`), `sale_record_options`. RLS: 옵션·규칙은 메뉴와 같음(규칙 품목은 같은 매장만), 판매 옵션은 보기만(함수로만 기록)
- DB: 내부 함수 `sale_ingredients(메뉴, 옵션들)`, `record_sales` 의 줄에 `option_ids`(같은 매장·보관 안 됨·중복 없음), `menu_sales_summary` 를 메뉴·옵션 묶음별로. 옵션 규칙에 쓰인 품목도 기본 단위 잠금
- core `options.ts`: `applyOptions`(DB 와 같은 계산), `optionLineName`. `menuProfitLines` 는 줄마다 재료비를 받도록 바꿈(옵션 묶음별 원가). 테스트 42개
- 메뉴 수익성 재료비가 옵션을 반영한다. 이론 vs 실제는 원장 합계라 자동으로 맞는다
- 만들다 고친 것: 규칙 모양 CHECK 가 수량 NULL 을 통과시키던 것(NULL > 0 은 NULL → CHECK 통과) → `IS NOT NULL` 추가 (`..._menu_option_rules_check.sql`)
- 확인: SQL 검증(core 와 같은 결과: 오트밀크+사이즈업+샷 → 오트밀크 300ml·원두 36g·큰 컵, 판매 금액·원장 메모, 옵션 묶음별 합계, 중복·없는 옵션 거부, 판매 옵션 직접 INSERT 거부, 다른 매장 사용자 0건, `sale_ingredients` 직접 호출 거부) + 새 E2E `options` + 전체 E2E

### 18. 메뉴 옵션 차감 2단계: CSV 옵션 열 (2026-10-08)
- 옵션 열을 낱말로 나눈다 (core `splitOptionNames`: 쉼표·슬래시·세로줄·가운뎃점·줄바꿈, 뒤의 "(+500원)"·"x1" 은 뗌)

  - 왜 세 가지인가: ICE·HOT 는 이 앱에서 옵션이 아니라 다른 메뉴(아메리카노·아이스 아메리카노)라서. "메뉴 이름에 붙임" 낱말은 메뉴 매칭 이름에 붙는다("아메리카노 / ICE")
  - 자동: 저장해 둔 매칭 → 옵션과 이름이 같으면 그 옵션 → 아니면 "메뉴 이름에 붙임"(옵션 기능 전과 같은 동작이라 예전 메뉴 매칭·기존 E2E 가 그대로 맞는다)

- `import_sales`: 줄마다 `option_ids`, 금액이 없으면 (메뉴 + 옵션 금액) × 수량, `sale_ingredients` 로 차감, 취소 줄도 옵션 재료까지 되돌림. 옵션은 같은 매장만(보관된 옵션도 받음), 중복 거부
- 행 키는 옵션 열 원문 그대로 → 낱말 매칭을 바꿔도 이미 가져온 판매는 다시 안 들어온다
- core 테스트 2개 추가(44개). E2E `options` 에 CSV 단계 추가: 자동 매칭, 무시하면 메뉴 단계에서 빠짐, 옵션·취소 줄 차감, 같은 파일 다시 올리면 매칭 기억·건너뜀
- 확인: SQL 검증(옵션 금액 포함 기본 금액, 다른 매장 옵션·중복 거부, 다른 매장 옵션으로 낱말 매칭 거부, option 인데 옵션 없음 거부, 다른 사용자 0건) + 기존 `sales-import` 시나리오 그대로 통과 + 전체 E2E

### 19. 소진 예상일·사용량 기반 발주 추천 (2026-10-09, 커밋 `b22b8f7`)
- 경쟁사 2차 조사의 꼭 필요한 기능 ⑦ (HANDOVER §10-0). 참고: 페이히어(품절 위험 예측), MarketMan(사용량 기반 추천 발주)
- 하루 평균 사용량 = 오늘을 뺀 최근 14일 판매·사용(consume) 합계 ÷ 날 수 (core `dailyUsage`)
  - 반품은 상계, 폐기·조정은 뺀다 (들쭉날쭉해서). 처음 쓴 날이 14일 안이면 그 날부터 세고, 3일보다 짧으면 평균을 내지 않는다
  - DB 함수 `item_usage_summary` (읽기 전용, SECURITY INVOKER): 기간별 품목 사용량 + 처음 쓴 시각(기간 전에도 썼으면 기간 시작). 화면은 `lib/item-usage.ts` `loadDailyUsage` 로 매장 시간대 14일을 넘긴다
- 거래처에 **입고까지 걸리는 날**(`lead_days`, 0~60, 기본 1)·**한 번 발주로 버틸 날**(`cover_days`, 1~90, 기본 7). 거래처 폼에 칸 추가
- 발주 추천 (core `reorderAdvice`, 웹 `itemReorderAdvice`·`buildOrderSuggestions`)
  - 발주할 때 = 재고 ≤ 부족 알림 기준 + 하루 평균 × 입고까지 (기준은 안전 재고 역할)
  - 수량 = 기준 + 하루 평균 × (입고까지 + 버틸 날) − 재고, 기본 입고 단위로 올림
  - 사용량을 모르면 예전 그대로(기준 이하일 때 기준 × 2). 그래서 기존 `orders` E2E 수량은 그대로 맞는다
  - 문구 "부족 품목 N개 담기" → "추천 품목 N개 담기"
- 보여주는 곳
  - 품목 목록: "약 6일 뒤 소진", 상태 필터 "7일 안에 소진 N" (`/items?status=runout`)
  - 품목 상세: "하루 평균 200g 사용 (최근 14일) · 약 6일 뒤 소진 · 지금 발주할 때 (입고까지 2일)"
  - 대시보드: "곧 떨어질 품목" (부족 품목을 뺀 7일 안 소진, 빨리 떨어지는 순, 발주할 때 배지, 사장·매니저에게 "발주하기")
- core `usage.ts` (테스트 4개 추가, 48개). 새 E2E `usage` (15개)
- 확인: SQL 검증(14일 합계·반품 상계·폐기 제외·기간 시작 처리, 다른 매장 사용자 0건, 익명 거부, 날 수 제약) + 새 E2E `usage` + 전체 E2E 15개 통과
- 남은 것: 입고 예정 수량을 빼고 추천하기(지금은 발주해 둔 품목도 다시 추천됨), 요일별 사용량, 품목별 버틸 날

### 20. 폐기 사유·폐기율 (2026-10-09, 커밋 `960ef81`)

### 21. 발주 추천에서 이미 발주한 수량 빼기 (2026-10-09, 커밋 `de94260`)
- 19 의 남은 것. 발주해 둔 품목이 들어오기 전까지 "발주할 때"로 보이고 새 발주서에 또 추천되던 문제
- core `reorderAdvice` 에 `incoming`(입고 예정, 기본 단위): 판단을 "재고(마이너스는 0) + 입고 예정"으로. 입고 예정이 없으면 예전과 같다
- 입고 예정 = 발주함·일부 입고 상태 발주서 줄의 (주문 − 입고) × 단위 환산 (`lib/order-suggestions.ts` `incomingQuantities`, `lib/item-usage.ts` `loadIncoming`). 작성 중 발주서는 세지 않는다 (지금 쓰는 발주서의 품목은 원래대로 추천에서 빠진다)
- 쓰는 곳: 발주 추천(새 발주·작성 중 발주서·추천 담기), 대시보드 "곧 떨어질 품목"(발주할 때 판단 + "입고 예정" 배지, 직원도 볼 수 있음), 품목 상세("입고 예정 2봉")
- core 테스트 1개 추가(51개). E2E `usage` 에 6단계: 발주하면 새 발주 추천이 없어지고 상세·대시보드에 입고 예정
- DB 변경 없음 (발주서는 구성원 모두 읽을 수 있음)

## 다시 시작하는 방법

처음 받는 PC라면 `git clone https://github.com/ll-lrv/cafe-manager.git` 후 `pnpm install`.

1. **Docker Desktop 실행** (`%LOCALAPPDATA%\Programs\DockerDesktop\Docker Desktop.exe`)
2. 로컬 Supabase 시작 (데이터는 그대로 남아 있음)
   ```
   npx supabase start -x imgproxy,edge-runtime,logflare,vector,supavisor
   ```
3. 웹 개발 서버
   ```
   pnpm dev
   ```
   → http://localhost:3000 · DB 보기: Supabase Studio http://127.0.0.1:55323
4. 처음부터 깨끗한 DB가 필요하면 `pnpm db:reset` (모든 계정·데이터 삭제)

로컬 DB는 2026-10-07 에 비웠고, 2026-10-08 에 데모 계정을 하나 만들었다: `demo-owner@cafe.kr` / `test1234` ("데모 카페").

`apps/web/.env.local` 은 git에 없다. 새로 받은 경우 `.env.example` 을 복사하고
`npx supabase status` 의 Publishable key 를 `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` 에 넣는다.
